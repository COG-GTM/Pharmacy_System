2. Current Monolith Architecture

The Pharmacy Management System is a Laravel 9 monolith (PHP 8.0.2) with a single MySQL database. It manages pharmacies, doctors, clients, orders, medicines, payments, and provides admin dashboards with revenue analytics.

3. Model Dependency Graph

User

app/Models/User.php | Fillable: id, name, email, password, email_verified_at, remember_token

Relationships: owns() → Pharmacy, client() → Client, orders() → Orders, pharmacy() → Pharmacy, doctor() → Doctor

Traits: HasRoles (Spatie), Bannable (cybercog), MustVerifyEmail

Pharmacy

app/Models/Pharmacy.php | Fillable: id, user_id, pharmacy_name, avatar_image, area_id, priority

Relationships: area() → Area, user() → User, doctors() → Doctor, orders() → Order

Traits: SoftDeletes

Doctor

app/Models/Doctor.php | Fillable: id, user_id, avatar_image, pharmacy_id, is_banned, banned_at

Relationships: pharmacy() → Pharmacy, user() → User

Traits: Bannable (cybercog)

Client

app/Models/Client.php | Fillable: id, user_id, gender, date_of_birth, avatar_image, phone

Relationships: user() → User, area() → Area, address() → Address (1:N), orders() → Order (1:N)

Order

app/Models/Order.php | Fillable: user_id, doctor_id, delivering_address_id, pharmacy_id, is_insured, status, creator_type, quantity, medicine_id, price

Relationships: pharmacy() → Pharmacy, user() → User, doctor() → Doctor, medicines() → Medicine (N:M), client() → Client, address() → Address

Static methods: totalPrice(), createOrderMedicine(), updateOrderMedicine()

Statuses: New, Processing, WaitingForUserConfirmation, Canceled, Confirmed, Delivered

Medicine

app/Models/Medicine.php | Fillable: name, type, quantity, price (in cents)

Relationships: orders() → Order (N:M via orders_medicines pivot)

Address

app/Models/Address.php | Fillable: client_id, area_id, street_name, building_number, floor_number, flat_number, is_main

Relationships: client() → Client, area() → Area, order() → Order (1:N)

Area

app/Models/Area.php | Fillable: id, name, address, country_id

Relationships: pharmacies() → Pharmacy (1:N), address() → Address (1:N), clients() → Client (1:N)

Payment, Prescription, OrderMedicine, Admin

Supporting models for payment tracking, prescription image storage, order-medicine pivot, and admin user management.

9. Data Migration Strategy

Database-per-Service Split Plan

Service DBTables from MonolithPort
auth_dbusers, password_resets, personal_access_tokens, roles, permissions, model_has_roles, model_has_permissions, role_has_permissions, bans3306
pharmacy_dbpharmacies, doctors3307
client_dbclients, addresses3308
order_dborders, orders_medicines, prescriptions3309
catalog_dbmedicines3310
payment_dbpayments3311
geography_dbareas, countries3312
analytics_dborder_stats (new), revenue_summary (new, materialized)3313

Migration Steps

  1. Run all service migrations to create schema in each DB
  2. Export data from monolith grouped by service context
  3. Import into respective service databases
  4. Verify row counts match between source and destination
  5. Validate referential integrity via cross-service API checks

Rollback Procedure

  1. Docker named volumes preserve all service data
  2. Monolith container remains available (just not routed to via gateway)
  3. Rollback = re-point Nginx to monolith container, stop microservice containers
  4. Data sync: Use event replay to reconcile any diverged state

10. Extraction Wave Plan

WaveServicesDependenciesRationale
Wave 1 Notification RabbitMQ only No database, lowest risk. Pure event consumer.
Wave 2 Geography, Catalog None Self-contained, no cross-service dependencies. Leaf services.
Wave 3 Auth None Core identity service. Must be extracted before services that create users.
Wave 4 Pharmacy, Client Auth Service Both create users via Auth Service. Can be extracted in parallel.
Wave 5 Order, Payment, Analytics All upstream services Highest coupling. Depends on Catalog, Geography, Client, Pharmacy, Auth.
